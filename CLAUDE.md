# CLAUDE.md — Woreda Administration Portal

Multi-tenant government ERP for the six woreda administration offices of the
Harari People's National Regional State, Ethiopia. Each woreda is a tenant;
staff register residents and households, issue residence ID cards, record vital
events, handle service-request letters and complaints, manage kebele rental
houses, collect revenue, and print reports.

Two portals off one app:

| Portal | Prefix | Language | Who | Shell |
|---|---|---|---|---|
| Super Admin Console | `/admin` | English | `super_admin` only | `AdminShell` (slate sidebar) |
| Woreda OS | `/woreda` | Amharic primary, English secondary | every other role | `WoredaShell` (navy `#1e3a5f` sidebar) |

Tenants are seeded, not created in-app: `AMIR_NUR`, `ABADIR`, `SHENKOR`,
`ABOKER`, `JINEALA`, `HAKIM`, with 19 kebeles between them.

> **`README.md` is a stale Phase-1 build spec, not a description of this
> codebase.** It calls for React 18, Vite 5, react-i18next, a PWA plugin and a
> `src/pages/` tree — none of which exist here. Its RBAC tables, schema and
> design tokens are also behind the code. Treat this file and the source as
> authoritative; only trust the README for product intent.

## Commands

Bun is the package manager (`bun.lock`); the toolchain itself is plain Vite.

```bash
bun install          # bunfig.toml enforces a 24h minimumReleaseAge on packages
bun run dev          # vite dev
bun run build        # vite build — also regenerates src/routeTree.gen.ts
bun run lint         # eslint (prettier runs as an eslint rule)
bun run format       # prettier --write .
bunx tsc --noEmit    # typecheck — there is no `typecheck` script
```

There is no test suite and no test runner in `package.json`. Verification is
`lint` + `tsc --noEmit` + a build, plus driving the affected page in a browser.

**Build before typechecking after any route change.** `src/routeTree.gen.ts` is
generated by the TanStack router plugin during `vite build`. Running
`tsc --noEmit` against a stale tree reports "not assignable to type" errors on
the new route that look like a mistake in the route file itself.

## Stack

- **TanStack Start** (React 19, Vite 8, nitro) — SSR-capable server, but see
  "Everything is client-rendered" below.
- **TanStack Router** — file-based routing from `src/routes/`.
- **TanStack Query v5** — every server read/write.
- **Zustand** — auth state only (`src/stores/authStore.ts`).
- **Supabase** — Postgres + Auth + Storage + Edge Functions. RLS is the
  authorization boundary.
- **Tailwind v4** (`@theme` in `src/styles.css`, lightningcss transformer) +
  **shadcn/ui** new-york, slate base, in `src/components/ui/`.
- **React Hook Form + Zod** for forms, **Recharts** for charts, **Leaflet** for
  GIS pickers, **jsPDF + html2canvas + react-to-print** for printing,
  **sonner** for toasts, **framer-motion** for page transitions only.
- Icons: **lucide-react** exclusively.

No i18n library. Amharic and English strings are written inline in components,
usually as `labelAm` / `labelEn` pairs or stacked spans.

## Routing

Flat, dot-separated filenames map to nested routes. `woreda.residents.$residentId.edit.tsx`
→ `/woreda/residents/:residentId/edit`. `src/routes/README.md` has the full
convention table. Do not create `src/pages/`, `app/layout.tsx`, or
`routes/_app/` — those are Next/Remix shapes and this router ignores them.

- `__root.tsx` is the only shell: `<head>` metadata, Google Fonts (Noto Sans
  Ethiopic + Inter), `QueryClientProvider`, `<Toaster />`, and
  `<AuthBootstrapper />`. Preserve its `<Outlet />`.
- `woreda.tsx` / `admin.tsx` are the portal layout routes. They block on
  `authStore.isLoading`, redirect to `/login` without a role, and cross-redirect
  `super_admin` ↔ everyone else. Section layout routes such as `woreda.civil.tsx`
  do nothing but render a `<ModuleGate>`.
- `index.tsx` routes by role *and* account status: `pending` → `/set-password`,
  anything other than `active` → `/login`.
- Public routes: `/login`, `/set-password`, `/verify/letter/$token`
  (QR letter verification, `noindex`, reads through a `SECURITY DEFINER` RPC).

### Everything is client-rendered

Every route file except `__root.tsx` sets `ssr: false`. Auth lives in
`localStorage` via the Supabase browser client, so a server render has no
session and would flash the wrong portal. **New route files must set
`ssr: false` too.**

### Three gates, in order

1. **Route guard** — `woreda.tsx` / `admin.tsx` decide portal access by role.
2. **`<ModuleGate moduleKey="…">`** — per-tenant feature flags from
   `tenant_module_config`. Redirects to the dashboard with a toast when the
   module is off. Missing config rows default to *enabled*.
3. **`<PermissionGate permission={P.X}>`** — hides a button or panel.
   `useAuthStore(s => s.hasPermission)` is the imperative form.

Sidebar items come from `NAV_PERMISSION_MAP`, filtered by permission and then
by module key. Never branch nav rendering on a role name.

## Data access

**There are no TanStack server functions in this app.** Every query and mutation
runs in the browser against the anon-key client:

```ts
import { supabase } from "@/integrations/supabase/client";
```

RLS is what stops cross-tenant reads — not the `.eq("woreda_id", …)` filter,
which is there for correctness and index use. Still always scope explicitly:

```ts
const woredaId = useAuthStore((s) => s.woredaId);

useQuery({
  queryKey: ["residents", woredaId, search, sort.key, page],
  enabled: !!woredaId,
  queryFn: async () => {
    const { data, error } = await supabase
      .from("resident")
      .select(RESIDENT_SELECT, { count: "exact" })
      .eq("woreda_id", woredaId as string)
      .range(from, to);
    if (error) throw error;
    return data;
  },
});
```

Conventions the list pages already share — reuse them rather than reinventing:

- Query keys start with the table name and include `woredaId` plus every filter.
- `enabled: !!woredaId` on anything tenant-scoped; `staleTime` around 5 min for
  reference data (kebeles, modules, service types, branding).
- Toolbar state lives in the URL: `useUrlSearchTerm`, `useUrlSort`,
  `useUrlPagination` from `TableToolbar` / `TablePagination`.
- Loading/empty/error rows: `TableSkeletonRows`, `TableEmptyRow`, `TableErrorRow`.
- Export via `exportRowsToCsv` / `exportRowsToPdf` with `useReportBranding()`.
- Mutations `invalidateQueries` on the same key prefix and `toast` the outcome.

**Never import `client.server.ts` from a route file or any module that reaches
the client bundle.** It holds the service-role key and bypasses RLS. If a
server-side path is ever needed, load it inside a server handler with
`await import("@/integrations/supabase/client.server")`.

ESLint blocks importing `server-only`; TanStack Start uses `*.server.ts`
filenames or `@tanstack/react-start/server-only` instead.

### Audit logging is manual

Every state-changing action inserts its own `audit_log` row from the client:

```ts
await supabase.from("audit_log").insert({
  woreda_id: woredaId,
  entity_name: "resident",
  entity_id: residentId,
  action_type: "update",
  old_value_json: before,
  new_value_json: after,
});
```

`actor_user_id` is overwritten by the `force_actor_columns` trigger, so a
client cannot forge it. The table has INSERT and SELECT policies only — it is
append-only by construction. Add the audit insert whenever you add a workflow
transition, and add the entity to the audit page's deep-link map.

## Authorization: two sources, kept in sync by hand

| Layer | Lives in | Used for |
|---|---|---|
| Static map | `src/config/permissions.ts` → `ROLE_PERMISSIONS` | UI gating only |
| Database | `default_role_perms(role)` + per-tenant `role_permission` overrides | Actual enforcement inside RLS |

`user_has_perm(_perm)` checks the `role_permission` row for
(woreda, role, permission) and falls back to `default_role_perms(au.role)` when
none exists — and requires `app_user.status = 'active'`. The Settings →
Roles & Permissions tab writes those override rows.

**Adding a permission touches three places:** the `P` object and the relevant
role arrays in `src/config/permissions.ts`, the matching arrays in
`default_role_perms()` via a new migration, and the RLS policies that should
honor it. Skipping the migration produces a button that renders and then fails
on the write; skipping the config produces the reverse.

`super_admin` and `tenant_admin` are deliberately absent from `role_permission`
(its CHECK constraint excludes them) — they resolve through `is_super_admin()`
and `is_tenant_admin()`.

Roles: `super_admin`, `tenant_admin`, `supervisor`, `civil_registrar`,
`registry_clerk`, `finance_clerk`, `auditor`, `viewer`.
Module keys: `credentials`, `civil_registration`, `revenue`, `reports`, `audit`,
`rental_houses`, `services`, `approvals`.

## Database

One baseline migration holds the whole schema (~36 tables, all with RLS
enabled). Add changes as new numbered migrations; don't rewrite the baseline.
`scripts/dump-schema.sql` / `dump-data.sql` regenerate a baseline from a live
project when that is genuinely needed.

Domain tables: `woreda`, `kebele`, `app_user`, `woreda_settings`,
`tenant_module_config`, `role_permission`, `household`, `resident`,
`residence_credential`, `credential_request`, `vital_event`, `service_request`,
`service_type`, `kebele_rental_house`, `rental_occupancy`,
`rental_occupancy_request`, `payment`, `receipt`, `fee_schedule`,
`id_card_template`, `audit_log`, plus `*_sequence`, `*_status_history`,
`*_document`/`*_attachment` and print-log satellites.

Views: `approval_queue_v` (a union of everything awaiting action across the
workflow tables — a read model, never written to) and `household_member_roster`.

> `approval_queue_v` is designed to run `security_invoker` so the underlying
> tables' RLS applies, and `/woreda/approvals` queries it with **no**
> `woreda_id` filter on that assumption. The baseline migration creates the view
> without that option — `pg_get_viewdef` drops reloptions, so the dump lost it.
> Check the deployed database and add
> `ALTER VIEW public.approval_queue_v SET (security_invoker = on);` in a
> migration if it is missing; without it the queue evaluates RLS as the view
> owner and can return other tenants' rows.

RLS helpers, all `SECURITY DEFINER` with a pinned `search_path`:
`get_user_woreda_id()`, `is_super_admin()`, `is_tenant_admin()`,
`user_has_perm(text)`, `user_has_any_perm(text[])`,
`storage_path_woreda_id(text)`.

### Business logic lives in triggers

Don't reimplement any of this client-side:

- **Reference numbers** are assigned on insert and must be left unset (or
  `'AUTO'`) by the client — `assign_resident_number`
  (`{WOREDA_CODE}-{SEQ:6}`, overridable per tenant via
  `woreda_settings.resident_number_format`), `assign_credential_number`
  (`WW-KK-YY-NNNNNN-C` plus a serial), `assign_credential_request_number`
  (`{CODE}-REQ-YY-NNNNN`), `assign_service_request_number` and
  `assign_rental_request_number` (`{CODE}-{TYPE}-YY-NNNNN`),
  `assign_receipt_number` (`{CODE}-RCT-YY-NNNNNN`), `assign_vital_event_number`.
- **Cascades on approval** — `generate_resident_on_birth_approval` creates the
  child's resident row from `event_details`, `apply_death_on_approval`,
  `apply_rental_occupancy_on_approval`, and
  `generate_residence_credential_on_payment` mints the credential when a
  request goes `paid`.
- **Guards** — `force_actor_columns` stamps actor/verifier/approver columns
  from `auth.uid()`; `validate_credential_fee_amount` and
  `validate_receipt_amount` reject mismatched money; `set_updated_at` maintains
  timestamps.

### Storage

Seven private buckets: `resident-photos`, `resident-clearance-letters`,
`credential-request-documents`, `rental-request-documents`,
`service-request-documents`, `credential-templates` (super-admin write, all
authenticated read), `tenant-assets` (logo, stamp, signature).

Reads go through signed URLs. Tenant isolation comes from
`storage_path_woreda_id(name)`, which reads the **first path segment** — so
every upload path must start `"<woreda_id>/…"` or the file becomes invisible to
its own tenant.

### Apply order

```
00000000000000_baseline.sql → 00000000000001_storage.sql → seed.sql → seed-app-users.sql
```

`seed.sql` is re-runnable (`ON CONFLICT DO NOTHING`). Its 972 `role_permission`
rows are the load-bearing part: without them no role resolves any permission
and every sign-in looks like broken auth rather than missing data.

## Edge Functions

`supabase/functions/`, Deno, deployed by `scripts/deploy-functions.sh <ref>`:

| Function | Does |
|---|---|
| `invite-tenant-user` | tenant_admin invites staff into their own woreda |
| `invite-platform-admin` | super_admin invites another platform admin |
| `resend-platform-invite` | re-sends a pending platform invite |
| `sign-credential` | RSA-signs the ID card QR payload |

`sign-credential` needs `HARARI_RSA_PRIVATE_KEY` in the function environment; it
is not in this repository. Without it the function deploys, runs, and returns
`500 {"error":"Signing key not configured"}`, and ID card issuance fails. The
matching public key is checked in at `src/config/credentialCryptoConfig.ts` for
offline verification.

# Environment gotchas

Problems that cost real time, and the fix that actually worked.

## Sandboxed agent environments (Claude Code on the web, CI containers)

Outbound traffic is restricted to HTTPS through a local proxy. Two consequences
that are not obvious from the error messages.

### 1. Headless browsers cannot reach the internet by default

Playwright/Chromium bypasses the shell's proxy settings, so every external
navigation fails with `net::ERR_CONNECTION_RESET` even though `curl` to the
same URL works. The proxy also terminates TLS, so its certificate is not one
Chromium trusts.

Pass the proxy explicitly and accept its certificate:

```js
const browser = await chromium.launch({
  executablePath: "/opt/pw-browsers/chromium-1194/chrome-linux/chrome",
  proxy: { server: process.env.HTTPS_PROXY },
});
const ctx = await browser.newContext({ ignoreHTTPSErrors: true });
```

`HTTPS_PROXY` is assigned per shell invocation and the port changes between
calls, so read it from the environment at launch. Never hard-code it, and never
disable TLS verification globally to work around it.

Testing against a *local* service (`127.0.0.1`) needs none of this.

### 2. Postgres ports are blocked; the Management API is the way in

`psql` to either the direct host or the pooler hangs and then times out:

- `db.<ref>.supabase.co` resolves to IPv6 only, which the sandbox has no route
  for, unless the project has the IPv4 add-on.
- `aws-0-<region>.pooler.supabase.com` resolves over IPv4 but ports 5432 and
  6543 are blocked outright. Port 443 to the same host is open, which is the
  tell that this is a port policy and not a Supabase problem.

Run SQL over HTTPS instead:

```bash
curl -X POST "https://api.supabase.com/v1/projects/$REF/database/query" \
  -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @payload.json     # {"query": "..."}
```

Build the JSON payload with a real serializer. Migration SQL contains quotes and
dollar-quoted function bodies that shell escaping mangles, and the failure looks
like a SQL syntax error rather than a quoting bug.

## Supabase

### Auth redirect URLs must be top-level, and allow-listed

For `POST /auth/v1/admin/generate_link`, `redirect_to` goes at the **top level**
of the body. Nesting it under `options` — which is where the JS client puts it —
makes the server ignore it silently and fall back to `site_url`:

```jsonc
{"type":"magiclink","email":"...","redirect_to":"https://app.example.com/"}   // honored
{"type":"magiclink","email":"...","options":{"redirect_to":"..."}}            // ignored
```

A URL that is not in `uri_allow_list` is also replaced by `site_url` with no
error. Both failure modes look identical, so when a redirect does not stick,
check the parameter position before assuming the allow-list is wrong.

Allow-list entries need the origin *and* a wildcard to cover both the bare
origin and sub-paths:

```
https://app.example.com/**,http://localhost:5173,http://localhost:5173/**
```

Keep these narrow. A pattern like `https://*.vercel.app/**` would let any site
on that domain receive users' auth tokens.

### Edge Functions are a separate deploy artifact

`supabase db push` and seed files do not touch them. Deploying is a
control-plane operation: a project `service_role` key cannot do it, only
`supabase login` or a Personal Access Token.

The CLI's `functions list` and `functions deploy` fail with `TransportError`
behind the proxy. The Management API works:

```bash
curl -X POST "https://api.supabase.com/v1/projects/$REF/functions/deploy?slug=$FN" \
  -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  -F "metadata={\"name\":\"$FN\",\"entrypoint_path\":\"index.ts\",\"verify_jwt\":false};type=application/json" \
  -F 'file=@index.ts;type=application/typescript'
```

To tell a deployed function from a missing one, call it unauthenticated. A
deployed function answers `401` with its own error body; a missing one answers
`404 {"code":"NOT_FOUND"}`. `scripts/deploy-functions.sh` wraps all of this.

## Vercel

### Deploy as an archive

`vercel deploy` uploads many files in parallel and dies partway through the
proxy with `fetch failed`, leaving a project that exists but has zero
deployments — so the URL 404s and it looks like the deploy never started.
`--archive=tgz` sends one tarball and gets through:

```bash
vercel deploy --prod --yes --archive=tgz --token="$VERCEL_TOKEN"
```

### Framework preset must stay "Other"

Nitro detects Vercel from the `VERCEL` env var and emits Build Output API v3
into `.vercel/output`. Setting the framework to `vite` makes Vercel look for a
static `dist/` instead and SSR breaks. Leave `framework: null` with
`buildCommand: bun run build`.

Do not pin a nitro preset in `vite.config.ts`. With none set, nitro builds
`node-server` locally and switches to `vercel` in CI on its own; pinning
`vercel` breaks local builds.

## This project

- Route files under `src/routes/` drive `src/routeTree.gen.ts`, which is
  generated at build time. After adding a route, run `bun run build` before
  `tsc --noEmit` — otherwise typecheck fails against the stale tree with
  "not assignable to type" errors that look like a mistake in the new route.
- `user_has_perm()` requires `app_user.status = 'active'`. A `pending` account
  authenticates fine and then sees every query return empty, with nothing in the
  UI explaining why. `index.tsx` sends `pending` accounts to `/set-password`
  because Supabase delivers invite links to the project's site URL.
- RLS lets a user read their own `app_user` row but not write it, so an account
  cannot activate itself. Activation is an administrator action by design.
- `client.server.ts` and `auth-middleware.ts` are unused generator output. Don't
  wire them up on a hunch — the whole app is browser-client + RLS, and
  introducing a service-role path silently removes the tenant boundary.
