MODULE PURPOSE
--------------
This module manages the full lifecycle of a Residence Credential request from
initial intake through physical printing and activation. It implements a strict
eight-stage maker-checker workflow with gated status transitions, payment
confirmation, credential generation, print logging, and audit trail writing at
every stage.

The Woreda Administration Office is the sole operational authority. Kebele is
a reference/location attribute only — not a workflow actor.

CREDENTIAL STATUS LIFECYCLE
-----------------------------
Implement as a strict finite state machine. No transition outside defined paths.

  Draft
    ↓ (clerk submits)
  Submitted
    ↓ (clerk/senior clerk reviews documents)
  Under Review
    ↓ pass verification         ↓ fail verification
  Verified                    Returned  ──→ back to Under Review on resubmit
    ↓ (supervisor reviews)
  Pending Approval
    ↓ approved    ↓ returned   ↓ rejected
  Approved       Returned     Rejected (terminal — closed)
    ↓ (cashier records payment)
  Awaiting Payment
    ↓
  Paid
    ↓ (system auto-generates credential record)
  Ready to Print
    ↓ (officer previews and confirms print)
  Printing
    ↓ (print job confirmed)
  Printed
    ↓ (resident collects — officer records acknowledgment)
  Active
    ↓ (event-based or manual)
  Expired | Suspended | Revoked | Replaced  (terminal states)

Store every transition in credential_status_history with:
  old_status, new_status, changed_at, changed_by_user_id, change_reason

Write a corresponding audit_log entry for every status change.

PRE-CONDITIONS — ENFORCED BEFORE REQUEST IS ACCEPTED
------------------------------------------------------
Before Stage 1 intake form is rendered or submitted, the system must validate:

1. resident.active_flag = true
   Failure: show error — "ነዋሪው ንቁ አይደለም። ወደ ነዋሪ መዝገብ ይሂዱ።"
   Block the request.

2. resident.current_household_id is not null AND household.active_flag = true
   Failure: show error — "ነዋሪው ከቤት ቁጥር ጋር አልተያያዘም። የቤት ዝርዝር ያስተካክሉ።"
   Block the request.

3. resident.residency_status ≠ 'Deceased'
   Failure: show error — block the request.

4. No active residence_credential record for this resident
   (residence_credential.status = 'Active' AND resident_id matches)
   If active credential found: show warning panel with the active credential
   details. Require clerk to explicitly select "Reissue" or "Renewal" type
   before proceeding. Do not silently override.

Run all pre-condition checks on resident_id entry before rendering the
intake form. Display a pre-condition summary card showing pass/fail for
each check.

STAGE 5 — CREDENTIAL RECORD GENERATION
-----------------------------------------
Trigger: Automated on service_request.status transition to 'Paid'
Actor: System (background job or on-transition hook)
Status transition: Paid → Ready to Print

SYSTEM ACTIONS (no UI interaction required, but show progress to user):

Generate and commit to residence_credential table:
  credential_number     — system-generated, tenant-scoped, UNIQUE
  serial_number         — sequential per tenant, formatted per woreda policy
  qr_payload            — signed token containing:
                            credential_number,
                            resident_id (resident_number),
                            issuing_office_id,
                            issue_date (ISO 8601),
                            expiry_date (ISO 8601),
                            checksum (HMAC or equivalent)
                          Store as signed string, never plain text
  issue_date            — today (Ethiopian calendar stored as Gregorian ISO
                          internally, displayed as Ethiopian in UI)
  expiry_date           — issue_date + configured expiry period
                          (read from woreda credential_policy config table)
  credential_type       — Card | Certificate | Both (from request)
  issuing_office_id     — current woreda office
  issuing_kebele_id     — resident's current kebele
  status                — 'Ready to Print'
  reissue_count         — 0 for new issue; increment for reissue/renewal
  reason_for_issue      — from request type

Create initial credential_status_history entry.
Write audit_log entry.

ON COMPLETION: Update service_request.status = 'Ready to Print'
Show status chip update to print officer's queue automatically.

AUDIT TRAIL — REQUIREMENTS
----------------------------
Every action in every stage must write to audit_log with:
  entity_name = 'residence_credential' or 'service_request'
  entity_id = relevant ID
  action_type = descriptive string (e.g., 'CREDENTIAL_APPROVED',
                'PAYMENT_RECORDED', 'CREDENTIAL_PRINTED', 'CREDENTIAL_REVOKED')
  old_value_json = prior state snapshot
  new_value_json = new state snapshot
  actor_user_id = authenticated user
  action_at = UTC timestamp
  source_ip = client IP where available

The audit log is immutable. Provide no UI to edit or delete audit entries.
The audit trail tab on the credential detail screen must display entries
in chronological timeline format with actor, action, timestamp, and
changed fields visible.

IMPLEMENTATION NOTES
---------------------
1. The QR payload must be a signed token, not plain text. Never expose
   raw resident data in the QR string.

2. credential_number and serial_number are immutable once generated.
   Never allow updates to these fields after Stage 5.

3. Old credential records must be retained with full history. Never
   delete or overwrite a credential record. Set status = 'Replaced'
   or 'Revoked' and create a new record for the replacement.

4. The system must enforce one active credential per resident at all times.
   Enforce this as a database constraint AND at application layer.

5. Verification endpoint (used for QR scan) must return INVALID for any
   credential in status: Expired, Suspended, Revoked, or Replaced.

6. All date storage is ISO 8601 Gregorian UTC. Ethiopian calendar is
   presentation-layer only.

7. Tenant_id must be included in every database query in this module.
   No exceptions.

8. The audit_log table is append-only. No update or delete operations
   are permitted on audit records under any role.

9. Print layout must use @media print CSS isolation. Navigation,
   sidebars, chips, and action buttons must not appear in print output.

10. Fee waiver still requires a zero-value payment record and receipt.
    This is an audit requirement, not optional.
